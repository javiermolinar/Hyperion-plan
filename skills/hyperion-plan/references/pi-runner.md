# Bounded foreground Pi assignment runner

`dist/pi-runner.js` is an opt-in ESM coordinator API, tested with the public Pi SDK **0.87.1**. It is not an auto-loaded extension, an automatic scheduler, or an implementation of the future `HostExecutionAdapter` lifecycle. Native Run supports coordinator-selected bounded `hyperion_wave` assignments and current-session sequential fallback. The native extension also exposes `hyperion_review` for explicit review requests, using this backend. Importing the module does not launch anything.

## Caller contract

The coordinator applies an explicit current implementation request and checkpoints the selected implementation step `in_progress` through the shared core first. It prepares a `WorkAssignment` from that exact canonical plan:

- `plan_path`: real absolute canonical path, not a redirect; `plan_id`, `approved_request_id`, `step_id` and `scope_digest` (shared `stepFingerprint(step).scope`).
- `owner`: `{host: "pi", native_id: ACTUAL_COORDINATOR_SESSION_ID}`. Never borrow an execution owner's ID.
- Unique opaque `assignment_id` and a separate attempt ID. A different ID does not evade request/step deduplication.
- Real absolute `cwd`, exact canonical file paths in `owned_paths`, explicit acceptance criteria, and the step's recorded effort preference.
- `evidence_directory: assignmentDirectory(plan_path, assignment_id)`. Evidence cannot be redirected to arbitrary files.

Call `runPiAssignment` with that assignment, the attempt ID, a synchronous **live** `authority()` gate, an explicit public `ModelRuntime` and model, original caller `thinkingLevel` (the inherit/fallback baseline), a tool allowlist, and explicit `contextFiles` (`[]` is valid). The gate returns `ExecutionAuthority`: current-turn authorization, current mode permission, request ID and actual actor ID. It is supplied by the embedding coordinator, not reconstructed from a ledger or saved selection. It is a cooperative host contract, not a security token.

```ts
import { runPiAssignment, assignmentDirectory } from "./dist/pi-runner.js";

const record = await runPiAssignment({
  assignment: {
    ...preparedAssignment,
    evidence_directory: assignmentDirectory(planPath, assignmentId),
  },
  attemptId,
  authority: () => currentCoordinatorAuthority,
  modelRuntime,
  model,
  thinkingLevel: "off", // original supported baseline; the step preference is applied before the first prompt
  tools: ["read", "edit", "write"],
  contextFiles: [{ path: requirementsPath, content: requirementsText }],
});
```

Only built-in `read`, `edit`, and `write` are accepted. Empty/read-only subsets are valid. Mutations are restricted to the declared exact files, with checks repeated at both the tool boundary and the public SDK filesystem-operation boundary. This also rejects SDK path normalization that would redirect a write/edit to an unowned file. Existing symlink aliases and multiply-linked files cannot be owned. The assigned canonical plan's Markdown/JSON, sidecar, export, recovery directory, lock and dispatch evidence are excluded. Shell, arbitrary custom tools, extensions, nested delegation, skill loading, prompt discovery, ambient AGENTS files and parent conversation history are not exposed. Both model and resources are explicit; the runner does not copy a parent registry or load credentials on its own. The supplied model runtime is trusted executable host code.

This is intentionally narrower than a general coding agent: the worker cannot run tests, create arbitrary files, or spawn a process. The coordinator handles broader validation. Fresh context is **not** process isolation or a filesystem sandbox. Standalone assignment reads can access files available to the process; wave reads are restricted to declared live inputs and owned files. Other actors or malicious providers can bypass cooperative locks. There is no OS-level protection against filesystem races. File ownership is enforced within an assignment, not by a global cross-plan workspace scheduler.

## Admission and durable records

The ledger lives at `<plan-directory>/.hyperion-dispatch/<plan-filename>/ledger.json`. Each assignment has a hash-named evidence directory. Records use shared `WorkAssignment`, `WorkerHandle`, `AssignmentResult` and coordinator verification contracts; their finer dispatch phases belong to this Pi backend rather than pretending the future generic adapter is implemented.

Admission takes the canonical plan lock and the short-lived ledger lock, rejects stale identity/owner/request/scope, unfinished prerequisites, unsupported barriers, absent start checkpoints, external refresh, paused/cancelled/finished plans, and false current-turn authority. An advisory freshness warning alone is not a blocker.

1. Persist **accepted** intent before any SDK session is allocated.
2. Persist **launching**, allocate a fresh persistent `SessionManager`, and save its native ID and reserved transcript path before the asynchronous SDK factory or prompt.
3. Revalidate authority before session construction and again before prompting. Keep the plan lock through prompt invocation, but release it before awaiting worker work. Each bounded tool rechecks current authority under that lock.
4. Record actual **started** from `agent_start`; append correlated lifecycle/tool/message event markers. This is distinct from accepted intent and SDK construction.
5. Await prompt completion, `waitForIdle`, actual `agent_settled` and ledger event writes. Persist the structured result and worker report, then **settled** or **failed**. SDK idle by itself is not treated as proof that arbitrary subprocesses stopped: implementation assignments admit none and await their built-in tool wrappers; review assignments additionally await host-controlled tests with their own quiescence contract.
6. Any ambiguous SDK, evidence or persistence exception after intent leaves **uncertain**, without claiming quiescence, rolling back files, resetting the step, or retrying.

Ledger writes use the existing atomic file writer (file fsync before rename), followed by directory fsync. Successful transcript/result evidence is flushed before recording the terminal result. These are separate atomic writes, not one filesystem transaction. Missing/corrupt history fails closed. This assumes the local filesystem honors locks, atomic rename and fsync; unsupported filesystem behavior is not hidden.

Pi 0.87.1 defers physical transcript creation until its first assistant message. The ledger therefore records a native identity and **reserved** path before model work, not a fictitious already-written transcript. Normal settlement requires an actual transcript. Failed setup may retain an identity with no transcript; that is ambiguous evidence to reconcile, not permission to relaunch.

Native review file lists are deduplicated before capture. Review preparation (authority checks and read-only capture) runs before SDK allocation: its typed failures do not create unknown-writer holds, so corrected input can proceed under the same current request without another approval. Supervisor cleanup completes before the call returns. Errors after that boundary remain conservative; neither an error-message match nor absence of a ledger row proves quiescence.

A repeated assignment ID, attempt ID, or plan/request/step tuple is rejected, including after a successful or failed result. Changing request/attempt IDs cannot bypass a prior active/uncertain record. Standalone assignments remain single-active per canonical plan. Only a locked durable wave reservation admits up to two specifically correlated members; unknown records and unreconciled wave claims hold further dispatch. There is no automatic redispatch or session resumption. See the foreground recovery API below; an ambiguous record without trustworthy settlement evidence remains blocked.

## Bounded implementation waves

`selectPiWave`, `piWaveConflict`, and single-use `PiWaveCoordinator` select and coordinate at most two explicitly supplied pending implementation candidates. Selection checks current authority, prerequisites, barriers, scope and effort; preserves explicit/legacy sequential order; and defers conflicting writes, live inputs and exclusive resources. Parallel-group badges alone do not establish independence. Missing concrete coordinator evidence produces a labelled sequential selection. Conservative path normalization serializes case/Unicode aliases. Shared interface/generator resources are exclusive coordinator-declared keys, not OS locks; no worker shell commands are admitted.

`runPiWave({waveId, candidates, authority, modelRuntime, model, thinkingLevel, signal?, onProgress?})` is the production SDK adapter. Candidates contain the usual assignment plus `attempt_id`, exact `read_paths`, exclusive `resources`, and concrete `independence_evidence`. Unlike standalone `runPiAssignment`, these steps must be pending: the adapter durably reserves their claims under the canonical/ledger locks and saves each individual start before dispatch. It rechecks after each checkpoint and again at locked SDK admission. Only the exact reserved members may overlap; separate controllers, new request IDs and ordinary dispatch cannot bypass an unreconciled reservation. Each member persists its native ID, transcript, effort and terminal evidence. Reads are restricted to declared inputs and owned files. No shell, inherited history or nested delegation is exposed.

The controller stops affected dispatch on failure, aborts peers and joins every launch promise. It returns successful, partial, cancelled and unknown outcomes separately; there is no rollback, automatic refill, redispatch or canonical completion. Repeated wave IDs inspect the existing reservation, even if interrupted. Restart-style ambiguous reservations remain held, not automatically closed or resumed. Trusted embedding hosts using the lower-level injected ports remain responsible for the same invariants.

After all writers stop, inspect and integrate actual files, run appropriate checks, and call `verifyDispatch` for each successful assignment. Verification records the integrated file hashes separately from the original worker result, allowing deliberate coordinator integration changes. The native mutation and CLI storage boundaries reject wave completion without the actual assigning actor, the same current approved request/selection, a ready started scope, coordinator verification and matching integrated bytes. They recheck both the pre-completion authority and the resulting write: another session, a new Run selecting the same step, or a paused/cancelled/unselected scope cannot reuse old verification. CLI callers supply their actual `--task-id` even when no handover owner is set. Pure model transitions and manual filesystem edits are not execution APIs. Checkpoint each verified completion separately; record incomplete results/blockers for failed or checkpointed-but-unlaunched work. Then call `reconcilePiWave(planPath, waveId, authority, evidence)` to release claims. Unknown/active writers, missing verification, changed integration bytes and unrecorded failures remain held. Failed work must be acknowledged as incomplete before ordinary coordinator follow-up; reconciliation does not claim that a failed worker succeeded. Evidence assertions remain the coordinator's responsibility, not independently established truth.

Native `hyperion_wave` exposes `run`, read-only `inspect`, `verify`, and `reconcile`. Run takes exact request/wave IDs, explicit step/file/read/resource/independence assignments, `current_request_authorized: true`, and `worker_sessions_authorized: true`. These cooperative assertions require current user authority; never derive them from saved state. The tool uses the actual coordinator session and public selected-model proxy. It reports saved starts and terminal results inline without opening a screen or starting a turn, and joins active workers on shutdown/reload/switch. Unknown writers veto switching and hold the host. A clean session-start re-enables admission, not execution. Native Run preserves an existing sequential preference and defaults new scopes to auto; the coordinator may choose labelled current-session sequential fallback. Coordinator ownership transfer is a separate [native handover workflow](pi-handover.md), never a worker assignment.

Synthetic component tests cover injected coordination ports. Separate actual SDK/scripted-provider tests establish two-worker overlap, capacity, native-tool transport, claim deferral, read restrictions, boundary revocation, duplicate-controller protection, failure/partial results, cancellation, restart-style durable holds and verification/checkpoint/reconciliation ordering. These do not establish OS isolation, arbitrary provider safety, live-model routing, actual process-kill recovery, or an independent review.

## Foreground cancellation and recovery

`runPiAssignment` accepts a caller `signal`, an optional `timeoutMs` execution deadline and `quiescenceTimeoutMs` (default 5000 ms). While active it polls current canonical authority every 50 ms; pause, cancellation, finish, scope/request/owner changes or a revoked live gate request SDK abort. Every tool also checks authority and the combined abort signal before work. The execution deadline and authority monitor start before the asynchronous SDK factory. Construction races the cancellation join deadline inside the canonical lock: a stalled factory releases that lock with an `uncertain` record, not a quiescence claim. A late session is disposed without prompting or changing the record; late rejection remains observed. The durable uncertainty still blocks dispatch, integration and transfer. Normal cancellation waits for the actual prompt, SDK idle/settled state and tracked tool promises. A deadline without those observations records `uncertain`, not success or verified cancellation. Existing file changes are not rolled back. Late responses cannot reset that record or grant approval.

`PiAssignmentSupervisor` owns foreground assignments supplied explicitly by its embedding coordinator. `stop(reason)` closes admission, aborts all active assignments, and joins every result with `allSettled`, including peers after one rejection. It reports unknown quiescence conservatively after any unresolved failure and forbids further dispatch. It is not a scheduler and does not allocate parallel waves. `bindPiAssignmentLifecycle(pi, supervisor)` connects an embedding extension's shutdown/reload and before-switch events; unknown writers veto switching. Install this binding in any host that uses the supervisor. Native wave execution installs its own stop/join hooks; neither the supervisor nor a session-start event resumes saved work. Source shutdown cannot be prevented at OS kill time; durable ambiguous records remain the recovery boundary.

Default SDK retry/compaction remain disabled. A trusted coordinator can supply `runtimeSettings` for those two SDK settings; completion still waits through them to actual `agent_settled` and idle, not `agent_end`. Implementation assignments still expose no unrestricted shell/custom worker tools and admit no command descendants. Review assignments may invoke only fixed host-controlled tests; their separate executor must join admitted processes or return unknown quiescence. Implementation writes use bounded synchronous filesystem operations within awaited built-in wrappers. Unmanaged external processes and arbitrary provider side effects remain outside the cooperative guarantee.

`recoverPiAssignment(planPath, assignmentId, authority)` can reconcile a result that was flushed before a ledger/checkpoint interruption. It checks native transcript/assignment/attempt correlation, the final settlement event, structured result, and declared-file digests. It never launches, resumes, integrates, or checkpoints a step. Current recovery authority and owner are required; recovering historical evidence is permitted while execution is paused, but `verifyDispatch` still rejects its acceptance against paused/revoked/changed scope. Missing results, mismatched evidence or changed files remain unknown and require manual reconciliation. Existing terminal records are returned idempotently without a new revision or model call.

## Settlement is not completion

`result.outcome === "succeeded"` means the SDK settled with a normal final assistant response and no tool errors. It does **not** mean the step's acceptance criteria passed. `changed_paths` compares the declared files before and after the run; it does not attribute concurrent external changes to the worker. The raw `worker_report` is untrusted prose, and its result file always carries `acceptance_verified: false`.

The coordinator inspects the actual files, transcript, tests, and ownership, then may call:

```ts
await verifyDispatch(planPath, assignmentId, () => currentCoordinatorAuthority, {
  acceptance_met: true,
  integration_checked: true,
  evidence: ["Concrete checks the coordinator actually performed"],
});
```

This rechecks current plan/request/owner/scope and records a separate verification field in the ledger. It validates correlation/evidence shape, not the truth of those assertions. Neither worker settlement nor this function writes canonical progress. A separately authorized coordinator checkpoint remains necessary to complete the step.

## Per-step effort

The fresh child applies the canonical step preference during session setup, before its first model request. It uses the public session's `getAvailableThinkingLevels()`, maps Hyperion `none` to Pi `off`, and maps `inherit` to the caller's original supported setting. Unsupported levels retain that setting with an explicit limitation; they are never passed to Pi's clamping setter. Requested preference, baseline, actual SDK setting and model are persisted before prompting and repeated in result evidence. A changed canonical preference rejects stale assignments.

For an existing SDK coordinator, `createSessionEffortController(session)` captures the original setting once. Its `run(preference, async evidence => { ... }, signal?)` applies an override only while idle, awaits the supplied model work, and restores the original setting after success, failure or cancellation. Concurrent scopes on the same session are rejected; separate sessions do not share effort state. Cancellation awaits SDK abort/idle before restoration. A model switch that makes restoration unsupported produces an explicit error instead of a silent clamp. This scoped helper does not authorize work or launch a session. The embedding coordinator must enforce canonical execution admission itself.

Native Pi Run still executes through the agent-mediated current-session fallback; it does not expose an SDK session to model tools or automatically apply these overrides mid-response. That boundary remains explicitly unsupported rather than falsely reported as applied. The SDK current-session and child paths are tested at the actual provider boundary; a native-host integration can call the same policy only at a supported boundary.

## Snapshot-bound reviews

`runPiReview` (or `supervisor.review`) handles `intent: "code-review"` with an explicitly selected, started review step, and `intent: "plan-review"` with an explicitly requested independent `plan_reviews` record. Supply `planPath`, optional code-review `stepId`, the Git-root `source`, explicit root-relative `files`, `attemptId`, live `authority`, `modelRuntime`, `model`, and original `thinkingLevel`. Optional signal/deadline semantics match the runner. Ordinary Check plan freshness cannot satisfy independent-review admission. Neither API writes canonical review outcomes.

The native `hyperion_review` tool takes the canonical path, exact request ID, intent, optional review-step ID, relevant file list, and the coordinator's `current_request_authorized` assertion. That flag has the same cooperative current-turn contract as the embedding gate; it is not proof of user consent or a security token. Never set it from saved approval alone. Code-review Run instructions name this tool only when review steps were explicitly selected. The tool uses the actual coordinator identity, selected model and effort baseline. Public `ModelRegistry.streamSimple` proxies that one chosen model into an explicit child runtime; no private runtime fields, parent transcript, ambient extensions or provider catalog are copied. Shutdown/reload/switch hooks stop and join supervised reviews. Native implementation assignments and handovers are not enabled by this review tool.

Before capture, the backend requires all earlier plan-local dispatch records to have verified writer quiescence and all implementation waves to be reconciled. Other hosts/external writers must also be drained by the coordinator; this is not a global workspace scheduler. The capture includes separate HEAD-baseline, staged-index and working copies of each supplied file, including untracked additions and deletions, plus modes and content hashes. Its manifest/digest and canonical requirements digest are persisted with the assignment before prompting. Captures require an existing Git HEAD and a resolved index. Non-Git/unborn repositories, symlinks, dependency/control/session files and oversized captures are unsupported, not silently approximated. Limits: 2000 explicit files, 2 MiB per blob and 16 MiB aggregate content. Git reads do not modify the worktree/index and disable fsmonitor/lazy network fetching. Snapshot files are read-only by convention/permissions, not an OS sandbox.

Code-review briefs use the existing exporter. Plan-review briefs distinguish targeted requirements from prerequisite/downstream context, preserve the requested focus and label missing original-user requirements. Prior progress and review notes remain labelled evidence, not an independently established verdict. A plan changed before its independent request is dispatched must be reconciled; an existing task ID must be inspected rather than replaced. Relevant requirements changing after capture prevent acceptance.

The fresh reviewer receives only `read`, literal `search_review`, `test_review`, and `report_review`. Reads are limited to manifest-listed captures and vetted test artifacts. No edit/write, shell, canonical-plan tool, ambient skill or recursive delegation is exposed. `report_review` accepts the exact snapshot digest and one numbered result per required check (`passed`, `finding`, `not-verified`, evidence, blocking flag). Normal final prose without that report cannot settle successfully. The report, controlled-test evidence, native session tag, assignment, attempt and snapshot stay correlated in the ledger/result/transcript. Duplicate calls return the existing review record, including interrupted/uncertain records; they do not start a replacement reviewer.

### Controlled tests and acceptance

An embedding coordinator may supply `reviewTests`, a map of fixed IDs to trusted `{ description, run(cwd, signal) }` functions. They are host code, never model-supplied commands or repository-discovered scripts. Each test runs once in a separate writable copy of the captured working files. It returns `status`, concrete `evidence`, and `quiescence` proof; generated files are retained and hashed. The original capture and source must remain unchanged. The harness owns cancellation and descendant joining; a throw or unknown quiescence leaves the assignment uncertain and the test copy preserved. This contract is not process isolation or a promise that arbitrary shell code is safe.

The native tool now supplies fixed suites without a separate embedding: captured Node packages with `tests/*.test.{js,cjs,mjs}` expose `<package-directory>:node`, and TypeScript packages expose `:typecheck`. Hyperion's own package additionally exposes `:build`, `:browser`, `:terminal-execution` and `:terminal-handover` for its existing entry points. No package.json script, shell string, reviewer-supplied argument or repository callback is executed as a command definition. Suite IDs are required in the captured review context; verification and canonical completion reject omitted, failed or unavailable suites even if the reviewer claims a pass. Repeated IDs reuse their one retained result. Other test frameworks still need an explicitly vetted embedding; their absence is not a pass.

A review request authorizes running the project's captured tests as **trusted local code**, not as hostile/sandboxed programs. Tests themselves are executable code. Each suite gets its own writable snapshot copy, cloned installed dependencies (no shared writable node_modules and no installs), isolated HOME/TMP and an allowlisted environment without provider credentials or user Node options. Captured package/lockfiles must match the installed dependency inventory; cloned input tree hashes are recorded. Missing capture inputs, dependencies, platform support or resources return `not-verified`. Build checks compare rebuilt and shipped bundles. This is not OS filesystem/network isolation, protection against malicious test code, or proof of arbitrary external writer quiescence.

A native review request runs in one call. After checking current canonical authority, the tool resolves existing test resources and launches the requested reviewer without a setup dialog, injected follow-up or second Run. Missing test dependencies/resources remain per-suite `not-verified` results; they do not prevent source review. Required-suite verification still rejects missing evidence, so running a review is not the same as passing acceptance. Cancellation, changed ownership/scope and duplicate-dispatch checks remain enforced. There are no automatic installs/downloads or retries.

Resolution preserves valid configured paths and explicit environment overrides. For missing or stale saved paths it inspects bounded conventional locations: installed project/Pi-local Playwright, Chromium on PATH or in browser caches, and installed Visualize plugin versions (including siblings of an expired version). It does not execute candidates, crawl arbitrary HOME directories, read credentials, or persist inferred paths. The selected paths are frozen for that review and recorded in test provenance. Malformed explicit configuration and missing resources remain visible as limitations.

Explicit setup/reconfiguration is still available separately through `hyperion_review_setup` (`request`, relevant `files`, and current user authorization). It is never offered by a normal review. This optional task uses a live, session-bound, expiring receipt for machine-local configuration saves and does not dispatch reviews. Installing/downloading or executing discovered programs is outside that standalone setup permission. Saved configuration is not a test result or authorization.

Resource settings are saved with private permissions under `<agent-dir>/hyperion/review/<sha256-of-real-project-root>.json`, outside the checkout. The agent directory defaults to `~/.pi/agent` (`PI_CODING_AGENT_DIR` overrides it). Browser/terminal resources use `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE` and (Hyperion browser only) `VISUALIZE_ASSETS`. Ordinary Node projects do not need Visualize. Precedence is host environment, machine-local project configuration, then legacy resource-only `.pi/hyperion-review.json`. Existing legacy files remain readable/captured; setup does not create or delete them. Values are existing absolute paths, never commands. Selected resource paths are frozen when the suite registry is constructed. Playwright/Visualize inputs are cloned and hashed; Chromium remains an identified external host runtime. The model still supplies relevant source/config/test files; an incomplete capture cannot silently count as the full suite. Resource inspection validates paths and basic installed-lock correspondence, not full runtime compatibility; execution can still report unavailable resources or dependency drift.

The fixed executor supports macOS/Linux, with a five-minute suite deadline, bounded output and TERM/KILL joining. A host-created Node preload records detached children synchronously (including ttyd/Playwright); ordinary descendants stay in tracked POSIX groups. Direct child close and empty live groups establish cooperative settlement. A leaked child makes the suite a finding even after cleanup; cancellation/timeout is not verified success. Unsupported accounting or unknown writers preserves the workspace and blocks review acceptance. Non-Node programs that deliberately escape process groups or test code that disables/tampers with accounting are outside this trusted-code contract. No sandbox or force-kill guarantee is claimed for them.

Retained, hashed evidence includes the log, command/environment provenance, dependency/resource hashes, result and bounded terminal screenshots/summaries. Larger scratch outputs remain in the isolated workspace but are not silently counted as hashed evidence. Cloned dependency inputs are removed only after verified settlement. The controlled-test API also supports a host-selected `artifact_directory` inside its disposable workspace; the default still hashes the entire workspace. Prior coordinator logs never become reviewer-run tests. The coordinator still inspects the report and evidence and writes completion separately; tests do not authorize fixes.

`verifyDispatch` additionally checks current requirements/source/index/modes, captured manifest/files, native transcript identity, report consistency and retained test artifacts. New code-review captures use `requirements_scope: "code-review-closure-v1"`: the requirements digest includes the review and its transitive prerequisite/timing closure, not unrelated plan steps. Adding or editing unrelated work therefore does not invalidate that review. Relevant requirements, dependency closure and source changes still invalidate acceptance. Legacy captures without this marker retain their original whole-plan digest; independent plan reviews also retain whole-plan validation because their reviewer receives that context. Any required not-verified check, omitted required native suite, or unresolved controlled test prevents verification. Code-review acceptance also rejects blocking findings. Independent plan-review verification instead confirms that the review was performed: supported findings, including blocking ones, may be reconciled without approving the proposed plan.

The canonical service and CLI enforce this evidence check when a managed code-review step or independent `plan_reviews` outcome first becomes completed. Code-review completion, including manual status/edit routes, requires the latest assignment for that plan/step, its assigning actor and current approved implementation request. Independent plan-review completion binds to its own explicit review request, latest managed attempt, assigning actor, native reviewer ID and exact result path; it does not require or resume an implementation selection. Both require recorded coordinator verification, successful settlement, unchanged requirements/snapshot and matching report/transcript/events/test artifacts. A new request cannot reuse an older clean report, bypass a failed/uncertain attempt, or relabel a known managed reviewer/report as external. Plan-review findings must be recorded with their reconciliation outcomes; `completed` means review performed, not plan approved. Missing required evidence leaves the managed outcome incomplete even when a report was delivered.

CLI callers supply their actual `--task-id` for managed completion even when no handover owner is set. Unmanaged/external reviews without a Pi assignment retain the shared-core contract; pure model transitions and direct file edits are not persistence APIs. These checks validate evidence shape and correlation, not the truth of model claims. The coordinator must still inspect coverage and evidence and use the current canonical revision to record the outcome. Independent plan-review outcomes use the existing `plan-review` operation and retain the native session ID/result path; foreground return does not retrospectively invent a running checkpoint. Preserve completed snapshot history when later plan corrections change requirements; the old report does not approve those changes. Findings never authorize code fixes, recapture or a second reviewer. Plan corrections follow the explicitly requested reconciliation policy.

## Verification

`npm run test:pi:runner` runs actual SDK sessions with a local scripted provider, isolated temporary workspaces, explicit model stores/resources and no network model calls or user credentials. Tests exercise the built bundle, native persisted transcript/assignment tags, file work, current authorization and ownership, locked admission, missing/stale scope, forbidden tool invocations, ambient-resource exclusion, duplicate/concurrent admission, ambiguous restored records, persistence faults, and verification-versus-completion. Review cases also exercise both intents, native tool/public-registry proxy, dirty captures, controlled artifacts, interruption and recovery. These are scripted SDK runtime tests, not live-model routing or an independent review of the implementation. Separate installed-terminal `test:pi:execution` and `test:pi:handover` fixtures verify native Run, wave/review effort and identities, inline draft preservation and persistent destination navigation. Their providers are also scripted. `HYPERION_KEEP_RUNNER_ARTIFACTS=1` retains temporary evidence.
